# 21 — «Дерево действий» для DistroTrace: корректность и спецификация

Дата: 2026-09-27. Neovim 0.11.4. Хост измерений: macOS 26.3 (arm64), **SSD, APFS** —
это НЕ целевая платформа потребителя (Windows/HDD). Все абсолютные числа ниже —
снижённая оценка; на HDD поправка кратно больше, и на главе 3 показано почему.

**Это исследование. Код не менялся, коммитов нет.** Артефакт — спецификация для писателя.

---

## Итог одной строкой

Честное дерево **возможно**, но не «дерево действий» в смысле «у каждого события есть
родитель», а **лес с явными асинхронными рёбрами**: реальная вложенность (синхронный
кадр) + честный разрыв на await-границе. Границу «до конечной отрисовки» измерьти
**нельзя** в headless и **нельзя надёжно** с UI — предлагаю измеряемую замену.
Накладные расходы ничтожны (0.0012 мс/событие), трейсить можно почти всё.

Три факта, где я **разошёлся с ТЗ** (в пользу кода — код прочитан, а не пересказан):

1. **Загрузчик УЖЕ трассится.** `lua/distro/loader.lua:96,158,194` — `loader:pack/<name>`,
   `loader:finish/<name>`, `loader:load/<name>`. Пункт 4 ТЗ («загрузка плагинов не
   трейсится») **устарел**. Это меняет приоритеты: не «добавить трейсинг загрузчика»,
   а **связать его существующие спаны с gd в дерево**.
2. **Накладные расходы не съедают смысл** — они в 400–2000 раз меньше типичной фазы.
   «Что не трейсить» в ТЗ — неактуально как ограничение по скорости; актуально
   только по объёму/читаемости лога.
3. **Парсер уже совместим с расширением формата** (глава 6) — риска падения на старых
   логах нет, ограничиваться 8 колонками не нужно.

## 1. Дерево в асинхронном коде — главный вопрос

### 1.1 Что я проверил

Вопрос не «вложится ли», а **вложится ли ПРАВИЛЬНО**. Синхронный кадр действительно
вкладывается, но модель «глобальный стек текущих спанов» ломается на интерливинге.

`/tmp/t4.lua` — решающий тест. Моделирую: `gd#1` нажат (ответ gopls ещё не пришёл), на
5 мс прилетает **посторонний** `CursorMoved`, на 8 мс пользователь жмёт `gd` второй раз:

```
t=0   enter gd#1                   depth=1 parent=nil
t=5   [unrelated CursorMoved fires, gd#1 still pending]
t=5   enter autocmd/CursorMoved    depth=2 parent=gd#1   <-- НЕВЕРНЫЙ РОДИТЕЛЬ
t=5   !!! attributed under: gd#1
t=8   [user presses gd AGAIN while gd#1 unresolved]
t=8   enter gd#2                   depth=2 parent=gd#1   <-- НЕВЕРНЫЙ РОДИТЕЛЬ
t=10  [gd#1 response arrives]
t=10  enter gd#1/lsp-response      depth=2 parent=gd#1
t=20  [gd#2 response arrives — which gd does it belong to?]
t=20  current stack top: gd#1      <-- ОТВЕТ gd#2 ЛЕГ НА gd#1
```

Вывод, который нельзя обойти: **однопоточность Lua не даёт родителя**. Между
`enter(gd#1)` и `leave(gd#1)` в стеке лежит всё, что угодно. «Стек» — это
игрушечная переменная, а не физическое свойство исполнения; на интерливинге она
называет чужую работу своей. Именно это и есть «ложь», которой ТЗ просит избежать.

Отдельно проверено (`/tmp/t3.lua`): `vim.schedule` и `vim.defer_fn` выполняются
при `depth=1` — то есть *на момент выполнения* кадра родителя уже нет, руками его
не удержать. Только явная передача контекста в замыкании.

### 1.2 Что вложится реально, а что — сирота

| Ситуация | Вложится? | Почему |
|---|---|---|
| Синхронный вызов внутри спана (`trace.span` вокруг `packadd`, `require`, `setup()`) | **ДА** | Один кадр Lua, вложенность физическая |
| `vim.lsp.buf_request` → колбэк ответа | **НЕТ** | Колбэк зовёт RPC-клиент из другого кадра |
| `vim.schedule` / `vim.defer_fn` (kick загрузчика) | **НЕТ** | `loader.lua:kick_deferred` возвращается мгновенно |
| LSP `on_exit` / `DiagnosticChanged` при загрузке | **НЕТ** | Событийный, без привязки к инициатору |
| Вложенный `M.load` внутри `M.load` | **ДА** | Реальный кадр; `load_depth` в loader это использует |
| Экран/отрисовка | **НЕТ** | Вне Lua вообще |

### 1.3 Предлагаемая модель: лес + асинхронное ребро

Вместо одного «дерева» — **лес корневых узлов**, где каждый узел несёт
`span_id`/`parent_id`, а потеря связи **обозначена явно**, а не молча.

Ключевое решение: **`parent_id` ставится только когда родитель доказуемо есть в
момент выполнения**. Доказательство = родитель в стеке кадров прямо сейчас.
Всё остальное — корень.

Три уровня, как просил ТЗ, плюс честный флаг:

- **Уровень 1 — «действие» (корень).** То, что пользователь нажал/произошло.
  Именно он отвечает на вопрос «сколько стоило моё нажатие».
- **Уровень 2 — синхронные фазы.** Реальные дети, сумма ≤ родителя.
  Пример: `gd` → `keypress_to_request` → `request_to_response` (часть внутри
  обработчика) → `response_to_cursor`.
- **Уровень 3 — вложенные спаны.** Например `loader:pack/gopls` внутри
  `loader:load/gopls`.

**Асинхронное ребро** — не ребро дерева, а **явная метка на узле**:
`async_from=<span_id>` + `kind = "response"|"scheduled"|"event"`. Читатель видит:
этот узел запущен изнутри того-то, но между ними был разрыв управления.

Формат (дописываются справа, старые 8 колонок не трогаются):

```
seq  t_ms  event  dur_ms  detail  buf  ft  run_id  span_id  parent_id  async_from
```

`span_id` — уникальный в пределах run, дешёвый счётчик. `parent_id` — `parent_span_id`
только для доказанных детей, иначе `-`. `async_from` — ссылка на инициатора
**без ложного вложения**.

**Почему не привязка по времени.** Тemptation: «ответ пришёл через 12 мс после
запроса — значит ребёнок». Это ровно та же ложь, только замаскированная: при
интерливинге из `/tmp/t4.lua` временнáя близость совпадёт с чужим родителем. Время
даёт **предположение** (`likely_from`), а не **факт** (`parent_id`). В ТЗ это названо
«привязка по времени» как вариант — отклоняю как основной механизм.

**Альтернатива, которую я рассмотрел и отверг**: перенос контекста вручную —
`vim.lsp.buf_request` враппер кладёт `ctx` в замыкание, а ленивый обратный вызов
`loader.kick` принимает `parent` параметром. Это **работает** и даёт настоящее
дерево для известных пар (запрос→ответ). Но требует явного изменения сигнатур
`M.load(name, parent)` и обёртки `on_exit`. Оцениваю как **фазу 2**: полезно, но
меняет публичный API загрузчика, а писателю на первом шаге нужен наблюдаемый
результат при минимальном риске. **Рекомендация: сначала лес + метки, затем
точечное переносы контекста для gd и загрузчика.**

### 1.4 Проверка, что модель не врёт

Свойство, которое надо сохранить: **сумма длительностей синхронных детей ≤
длительности родителя**, и ни один ребёнок не пересекает await-границу «молча».
Проверка — в тесте: синтетический gd с одним интерливингом (как `/tmp/t4.lua`),
утверждаем, что `CursorMoved` не стал ребёнком gd.

## 2. Граница «до конечной отрисовки»

### 2.1 Что показали измерения

`/tmp/t5.lua`, Neovim 0.11.4, `--headless`:

```
nvim_list_uis() (headless)            {}
has('gui_running')                    0
nvim_ui_attach Lua-callable           false / attempt to call a nil value
fn.screenchar callable                true
option redrawtime                     2000
nvim__redraw{grid=true}               false / invalid key: grid
content before/after redraw           alpha|beta  ->  alpha|beta
median 10x nvim__redraw (n=200)       0.2541 ms      => 0.0254 ms/call
median 10x nvim__redraw NOTIME (n=200) 0.2581 ms
```

**Прямой ответ на вопрос ТЗ: нет, headless не может.** Три независимых причины:

1. **UI не подключён** — `nvim_list_uis()` пуст. Нечего рисовать: нет grid, нет
   экрана, нет клиента.
2. **`nvim_ui_attach` из Lua недоступен** — это C API для встраивающих приложений,
   не функция `vim.api`. Проверено: `pcall` даёт `attempt to call a nil value`.
   То есть Lua-скрипт **не может** подключить UI, чтобы дождаться flush. Единственный
   путь — отдельный процесс-эмбеддер (тест через pty), а это уже другой инструмент
   и другой артефакт.
3. **`nvim__redraw` — константный no-op** (0.0254 мс/вызов, `notime` не отличается).
   Это не работа отрисовки, а фиксированный расход вызова. Считать его «отрисовкой»
   — враньё того же класса, что и уже избитый «мгновенное событие = полное время».

Про **с UI** честный вывод: даже с UI «мгновение завершения отрисовки» ненаблюдаемо
изнутри — нет колбэка «paint завершён». `redrawtime=2000` — это порог **подавления**
(для slow terminal), а не измерение. Любое число «до отрисовки» с UI — это
`t(после следующего кадра) − t(нажатие)`, то есть **измерение с потолком
ожидания**, а не факт отрисовки. Это верхняя граница, а не измерение.

### 2.2 Честная замена

Предлагаю **не** называть ничего «до отрисовки». Вместо этого — граница,
которую можно измерить и которая совпадает с тем, что пользователь ощущает как
реактивность:

> **`to_visible_state`** — момент, когда состояние редактора, которое нажатие
> изменило (курсор, позиция списка пикера, текст буфера), **записано в модель Nvim**
> и наблюдаемо через API. Это измеримо в headless.

`response_to_cursor` в текущем коде — почти это; разница в том, что оно меряется
внутри обработчика до того, как пикер реально перерисовался. Предлагаю:

1. **Переименовать** конечную фазу в `response_to_cursor` → оставить, но в UI
   подписать «курсор установлен (модель), не «экран обновлён»». Уже проделано для
   `dispatch only` — тот же приём.
2. **Добавить фазу `to_visible_state`**: `vim.api.nvim_win_get_cursor` + `nvim_buf_get_lines`
   подтверждают, что модель обновилась. Это измеримо, воспроизводимо, headless-совместимо.
3. **Явно написать в шапке отчёта**: «число измеряет момент доступности состояния
   для отрисовки; задержка фактического paint (обычно 1 кадр) не измерена и на HDD
   может добавить десятки мс».

### 2.3 Какое число окажется завышенным — и насколько

Никакое из доступных чисел не завышено «сверху» — они все **недобор**, и это важно
сказать прямо:

- `dispatch only` (0.1–0.6 мс) — **недобор на 1–2 порядка** (уже помечено в коде).
- `TOTAL` = `response_to_cursor` — недобор на величину одного кадра paint.
- На целевой платформе (HDD/Windows) добавляется ещё и задержка **доставки байтов на
  экран по сети/в эмулятор терминала**, которую этот инструмент в принципе не видит.

Практический вывод для потребителя: **инструмент показывает, где Nvim проводит
время, а не где терминал**. Для жалобы «5 секунд» этого достаточно (5 секунды
точно найдутся), для «200 мс против 240 мс» — нет, и спецификация обязана это
заявлять, иначе получится новый дефект веры в цифру.

## 3. Накладные расходы

### 3.1 Измерено

`/tmp/t6.lua`, реальный `distro.trace`, 0.11.4, median из 20000 прогонов:

| Сценарий | n | медиана | mean | p95 | сумма |
|---|---|---|---|---|---|
| A) хук с ранним выходом, трейс OFF | 20000 | 0.0000 мс | 0.0000 | 0.0000 | 0.60 мс |
| B) тело CursorMoved-автокоманды, OFF | 20000 | 0.0000 мс | 0.0000 | 0.0000 | 0.63 мс |
| C) тело CursorMoved, **ON** | 20000 | **0.0012 мс** | 0.0017 | 0.0051 | 34.71 мс |
| D) `M.span` (пустое тело), ON | 5000 | 0.0008 мс | 0.0012 | 0.0012 | 5.77 мс |

Вывод: **выключенный трейс действительно бесплатен** (A и B: сумма 0.6 мс на 20 000
событий = 0.00003 мс/событие, ниже разрешения таймера). Включённый — **0.0012 мс/событие**.

### 3.2 Верхняя граница на типовой сессии

Модель: 30-минутная сессия, 400 нажатий gd/gr (по ~6 строк), 30 открытий файлов
(по ~5 строк), прочее ~200.

```
6*400 + 5*30 + 200 = 2750 строк
```

Накладные = 2750 × 0.0012 мс ≈ **3.3 мс на всю 30-минутную сессию**.

Для сравнения: один жалованный лаг — 500 мс. Накладные трейса — **0.66 %** одного
лага, распределённые на полчаса. **Инструмент не может испортить то, что измеряет.**
Это прямо отвечает на «нельзя включать потребителю»: можно, и на HDD тоже —
см. ниже.

### 3.3 Почему на HDD вывод сохраняется, а сюжет про «съедает смысл» — нет

Числа выше — SSD/APFS. На HDD есть второй, настоящий риск: **`uv.fs_write` на
каждые 256 строк**. Это единственное место, где трейс касается диска. Но:

- flush асинхронный (`vim.schedule`), не блокирует UI;
- 256 строк ≈ 30–50 КБ, один append;
- даже на HDD это единицы мс и редко (не на каждое событие).

**НЕ ИЗМЕРЕНО**: реальная стоимость `uv.fs_write` на спин-диске. У меня нет HDD.
Число «3.3 мс» включает только CPU-часть; дисковую долю я оценить не могу и
заявляю это как непроверенное. Но даже при 10 мс на flush × 11 flushes = 110 мс
за полчаса — это 22 % одного лага и не объясняет 5-секундную жалобу.

### 3.4 Что всё-таки НЕ стоит трейсить

Не по скорости, а по читаемости и объёму:

1. **`CursorMoved`/`CursorMovedI` — только агрегаты, не построчно.** Это единственный
   источник тысяч строк (см. 3.2) и единственный, способный залить лог шумом.
   Ограничение: писать **не чаще 1 раза в 200 мс на буфер**, плюс счётчик
   подавленных событий в сводке. Иначе «какие действия» утонет в курсоре.
2. **Внутренние `require` внутри плагина** — лавина из сотен require'ов утонет
   смысл. Уже верно в коде: `loader.lua` трейсит **по одному спану на плагин**
   (комментарий на `lua/distro/loader.lua:143`). Сохранять.
3. **`DiagnosticChanged` при массовом обновлении** — одно событие, тысячи диагностик;
   трейсим **событие и количество**, не каждый элемент. Уже так и сделано.

## 4. Что должно попасть в дерево для нашей задачи

Приоритет пересчитан по факту, что загрузчик **уже** покрыт.

| Кандидат | Статус в коде | Приоритет | Обоснование |
|---|---|---|---|
| `_pick_lsp` (gd/gr/gi/gy) | **есть**, 3 фазы + TOTAL | **P0** | Прямая жалоба. Единственное, что отвечает на «нажатие → курсор» |
| Чтение файла / `BufReadPost` | только метка, **нет длительности** | **P0** | docs/19: чтение — главное. Сейчас не измеряется вовсе |
| `Syntax` | нет отдельного спана | **P0** | docs/19: второй по цене. Нужен свой спан вокруг syntax-этапа |
| `LspAttach` | метка, без длительности | **P1** | Нужна длительность (инициализация клиента) |
| Работа за ответом gopls | есть (`request_to_response`) | **P0** | Только эта фага показывает «сервер думал» vs «Nvim работал» |
| **Загрузчик (pack/finish/load)** | **уже есть** `loader.lua:96,158,194` | **P1** | Не «добавить», а **связать с деревом**: async-метка от `gd`, иначе лаг первого открытия файла будет вне дерева нажатия |
| `Distro*` команды | нет | **P2** | Потребитель жалуется на `gd`, не на `Distro`. Только если попросит |
| Пикеры mini.pick | нет | **P2** | Интересно, но вне жалобы. Ставить **после** P0/P1 |

**Главная поправка к ТЗ**: пункт «загрузка плагинов не трейсится — это критично»
**снимается**: покрытие есть. Остаётся **связать** — иначе при первом `gd` в новом
файле дерево покажет «gd = 12 мс» и промолчит про 4-секундную загрузку gopls,
произошедшую **рядом**. Это и есть главный риск вранья в этой задаче: **дерево
нажатия без асинхронной связи выглядит как «всё быстро»**.

Предлагаю правило: узел, у которого `async_from` указывает на `loader:*`, обязан
показывать это в сводке нажатия отдельной строкой, иначе дерево врёт.

## 5. Формат вывода в просмотрщике

### 5.1 Как выглядит «одно нажатие»

```
▾ gd — pick_lsp/definition                          5 032.4 ms   ██████████
    ├─ [sync] keypress_to_request                      0.8 ms
    ├─ [sync] dispatch (packadd gopls)               4 118.9 ms   ████▏  ← loader, async
    ├─ [sync] request_to_response                       0.3 ms
    └─ [async] lsp:definition response (gopls)        912.0 ms
    [async ← loader:load/gopls] 4 118.9 ms  вне дерева gd
    ───────────────────────────────────────────────────────────
    total in model (to_visible_state)               5 032.4 ms
```

Читается без контекста: видно, что **4.1 с из 5.0 — не gopls, а загрузка gopls с
диска**, а это ровно то, что нужно потребителю на HDD. Строка `async ←` не даёт
спутать «вложено» с «случилось рядом».

### 5.2 Обязательные элементы

- **Свои колонки `own` и `cum`.** Нынешний дефект (накопительная отметка в колонке
  длительности) воспроизведён в коде: `trace.lua` `M.sub()` пишет **кумулятивные** мс
  в поле `dur`, а `traceui.fmt_row` печатает `r.dur` в колонке «duration», и `M.rows`
  сортирует по `r.dur`. **Следствие: сортировка «дольше всех» ранжирует смешанные
  величины** — кумулятивные фазы всегда крупнее собственных. Подтверждено чтением
  `trace.lua:141-152` + `traceui.lua:150-158,120-126`.
  **Лечение:** новое поле `own_ms` рядом со старым `dur_ms` (старый не трогаем — см. гл. 6);
  сортировать по `own_ms`; в дереве печатать `own`, а кумулятивное показывать
  отдельно/в деталях.
- **Легенда символов** в шапке: `├─ [sync]` = реальный кадр, `[async]` = разрыв
  управления. Без легенды `[async]` читается как «ещё один под-этап» — то есть
  как раз та двухуровневая ложь, от которой предостерегает ТЗ.
- **Порог отсечения**: не показывать фазы < 1 мс по умолчанию (иначе в дереве 20 строк
  мусора), но показывать их количество: «+7 фаз < 1 мс (0.4 мс суммарно)».
- **Сводка «где время»**: сортировка по `own_ms` сверху — отвечает на вопрос
  потребителя напрямую.

### 5.3 Что делать с существующим дефектом накопления

Рекомендую **не ломать** старые логи: `dur` остаётся как есть (иначе старые логи
станут нечитаемыми), новое `own_ms` — единственная колонка для сортировки и деревьев.
Пока `own_ms` не заполнен, просмотрщик честно пишет «legacy: cumulative».

## 6. Совместимость формата

### 6.1 Измерено (`/tmp/t7.lua`, копия текущего `traceui.parse`)

```
legacy 8-field   ok=true  seq=1 event=pick_lsp/definition dur=nil  run=12345
new 11-field     ok=true  seq=1 event=pick_lsp/definition dur=500  run=12345
9-field          ok=true  seq=1 event=pick_lsp/definition dur=500  run=12345
```

Парсер **не падает** ни на 8, ни на 9, ни на 11 полях. Причина: разбор
`(line .. "\t\t\t\t\t\t\t")` добивает пустыми полями, а цикл жёстко обрывается
на `n > 8`. Лишние поля **молча отбрасываются** — то есть расширение формата
безопасно, но `span_id` так не достанешь.

### 6.2 Проверка детекта старого формата

```
old log: timed=0 slash_nodur=1 -> legacy label = YES
new log: timed=1 slash_nodur=1 -> legacy label = no
```

Детектор в `traceui.open()` работает корректно и на новом формате ложно
не срабатывает (появилась строка с длительностью). Хорошо.

### 6.3 Что обязан сделать писатель

- `parse` должен **перестать жёстко обрезать на 8** — читать по числу реальных
  разделителей, отсутствующие поля → `nil`. Тогда 8-колоночные старые логи дадут
  `span_id = nil`, и код обязан это переживать: **любая новая логика обязана иметь
  путь «span_id отсутствует»** (плоский вид, как сейчас).
- Никаких переименований/перестановки существующих 8 колонок: старые логи уже
  у потребителей на HDD, ломать их нельзя.
- Новые поля — только **справа и опционально**.
