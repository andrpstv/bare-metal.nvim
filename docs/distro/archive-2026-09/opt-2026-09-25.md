## 2. Пункт 1 — `git_sync_colors`: убран синхронный I/O на каждом старте

> **РАЗДЕЛ ПЕРЕПИСАН.** mtime-кэш, описанный ниже, **удалён** после ревью: он проверял
> метаданные вместо содержимого и менял поведение (см. врезку). Реализация теперь —
> отложенный вызов `vim.defer_fn` с разрешением путей на горячем пути.
> Актуальное описание: `docs/opt-2026-09-25-defer.md`. Историческая запись сохранена.

**Файл: `lua/core/init.lua:153-305`** (функция целиком; новая константа
`GIT_COLORS_CACHE_VERSION` — `lua/core/init.lua:153`).

> ⚠️ **ПРИНЯТОЕ ИЗМЕНЕНИЕ ПОВЕДЕНИЯ (исправлено).** Кэш по mtime ломал семантику
> «если ещё не записано»: если секция `[color "diff"]` удалялась из `.gitconfig`, но
> mtime сохранялся (`cp -p`, `tar --touch`, Time Machine, `rsync -t`), секция больше
> **не перелечивалась** до смены mtime. Раньше перелечивалась всегда. Это следствие
> выбора mtime-ключа, а не баг. Исправлено удалением кэша (defer-документ).

Что было сделано в этой (заменённой) версии:
- Результат кэшируется в `<lazygit_dir>/.nvim-git-colors.cache`.
- Отпечаток валидности: `version | mtime(.gitconfig) | mtime(lazygit/config.yml) | green | red`.
  Валиден → возврат без чтения **исходных** `.gitconfig`/lazygit-файлов (остаются 3 ×
  `fs_stat` + чтение самого кэша).
- Кэш пишется **после** всех мутаций, поэтому отпечаток соответствует состоянию,
  которое функция сама же и создала.
- Изменение `.gitconfig` (mtime) или палитры → автоматическая инвалидация и полный обход.
- Сохранены без изменений: ветка win32 (`$USERPROFILE`, `$APPDATA`), гард от литерального `$`
  в пути (`gitconfig:match("%$")`, `lg_dir:match("%$")`), аппенд color-diff и генерация
  темы lazygit.

Проверка (в песочнице `/tmp/sbx_gsc` с фейковым `$HOME`, реальный `~/.gitconfig` не тронут;
`sync_git_colors` принудительно `true`, т.к. в дефолте он `false`):

| сценарий | ожидание | результат |
|---|---|---|
| холодный старт, пусто | создать всё | `.gitconfig` + `lazygit/config.yml` + кэш — OK |
| тёплый старт | не трогать файлы | mtime/размер `.gitconfig` **не изменились** — OK |
| секция удалена, mtime восстановлен | кэш маскирует | секция **не** возвращена — это **изменение поведения, а не OK** (ручное удаление секции перестало перелечиваться; триггеры `cp -p` / `tar --touch` / Time Machine / `rsync -t`; лечится сменой mtime либо бампом `GIT_COLORS_CACHE_VERSION`). **Устранено** удалением кэша, см. `opt-2026-09-25-defer.md` |
| `touch .gitconfig` (новый mtime) | инвалидация | секция **возвращена** — OK |

Замеренная стоимость (микробенч, 50 итераций):
- старый путь (полный I/O каждый старт): **0.0677 мс/вызов**
- новый путь (тёплый кэш): **0.0487 мс/вызов**

На уровне полного старта разница **в шуме** (sync OFF 23.56 / ON тёплый 23.32 / ON холодный
23.61 мс медиана).

> ⚠️ **УТОЧНЕНИЕ ОТ 2026-09-25 — этот пункт не даёт выигрыша ВООБЩЕ, а не «в шуме».**
> `settings.sync_git_colors = false` (`settings.lua:101`), гвард в `init.lua:207` выходит
> на первой строке. При дефолтной конфигурации функция **не вызывается ни разу за
> сессию**: подтверждено тем, что после реального старта nvim в `~/.config/lazygit`
> не появляется ни файла кэша, ни записей. Вклад пункта 1 в измеренный выигрыш —
> **ровно 0 мс**, независимо от типа диска. Обещание «десятки мс на HDD» из
> `audit-2026-09-25.md` §3 п.6 **ложно** и там же исправлено.
> Все микробенчи выше — замер стоимости кода, **который по умолчанию не исполняется**.
> Реализация продолжена как подготовка к opt-in включению фичи; см.
> `docs/opt-2026-09-25-defer.md`.
>
> **Формулировка для читателя этого раздела:** оценка 2–5 / 30–80 мс — расчётная,
> но при `sync_git_colors = false` (дефолт) пункт **не исполняется вовсе**, поэтому и
> на HDD-VM обещанного выигрыша не будет — считать нечего, кода на горячем пути нет.
> **Вклад в измеренные ~1.5 мс равен нулю, весь выигрыш из devicons (3→1) и настроек порогов.**
>
> **Откуда тогда взялись ~1.0–1.5 мс.** Целиком из пунктов 2 и 3:
> дедупликация `nvim-web-devicons` (3 → 1 sourcing, `loader.lua:61-73`) и вынос
> порогов в настройки. Пункт 1 в этой сумме — **ноль**.

## 3. Пункт 2 — `loader.lua`: убран повторный `packadd` для `kind="start"`

**Файл: `lua/distro/loader.lua:61-73`** (блок `if ok then ... packadd`).

Было:
```lua
local pok = pcall(vim.cmd, "packadd " .. entry.name)
if not pok and entry.kind ~= "start" then ok = false end
```

Стало: для `entry.kind == "start"` `packadd` не вызывается вовсе (плагин уже в rtp и его
`plugin/*.vim` уже sourced при старте). Обход `deps` не тронут — зависимости по-прежнему
рекурсивно проходятся и `packadd`-ятся. Логика ошибок сохранена: `start` и раньше не был
fatal, поведение `ok = false` не изменилось.

Построчное подтверждение (`--startuptime`):
- **до:** `nvim-web-devicons/plugin/nvim-web-devicons.vim` sourced **3 раза**
  (0.158 + 0.008 + 0.019 мс)
- **после:** **1 раз** (0.215 мс) — остался только eager-стартовый

Функциональная проверка: `require("nvim-web-devicons")` → OK, `get_icon("lua","S")`
возвращает глиф шрифта (нерд-иконка на месте), `setup` — функция. Стартовые команды
`ConfigHealth` / `Format` / `Distro` на месте, `colors_name = khold` (тема не мигнула).

## 4. Пункт 3 — `large_file`: порог сделан настраиваемым

**Файлы:** `lua/core/settings.lua:79-94`, `lua/core/large_file.lua:1-40, 76-95`.

Новые настройки:
```lua
settings["large_file_max_lines"] = 5000   -- 0 = отключить проверку по строкам
settings["large_file_max_kb"]    = 1024   -- 0 = отключить проверку по размеру
```

Обоснование дефолта (не «молча снизил»):
- Исходный кейс — **~5000-строчные Go-файлы**, которые при пороге 10000 проходили как
  обычные и платили полную цену treesitter + gopls.
- 5000 — минимальный «круглый» порог, который реально накрывает жалобу.
- Сравнение изменено на **`>=`** (было `>`): при строгом `>` файл **ровно** в 5000 строк
  не попал бы в large_file — то есть дефолт 5000 не вылечил бы исходный кейс. Это главная
  причина, почему «просто поставить 5000» было бы неверно.
- Порог честно настраивается: 0 выключает измерение, 10000 возвращает старое поведение,
  3000 — агрессивнее.
- Риск признан: treesitter/LSP отключатся на 5000-строчных файлах, где они были нужны.
  Это осознанный размен на «открытие не тормозит»; владелец может поднять порог.

Проверка:
| файл | результат |
|---|---|
| 100 строк, Go | `large_file = nil`, `filetype = go` — не задет |
| 5002 строки, Go | `large_file = true`, `filetype = off`, `lsp_disable = true` — цель достигнута |
| `large_file_max_lines = 0` | `large_file = nil` — отключение работает |

Попутно исправлен баг: при `large_file_max_lines = 0` внутренний `max_lines()` даёт
`math.huge`, и `string.format("%d", math.huge)` бросал бы ошибку внутри `vim.schedule`.
Теперь сообщение формируется только при конечном пороге.

## 5. Пункт 4 — lock-файлы: две находки аудита НЕ подтвердились, файлы не удалены

Задание предписывало удалить `distro-lock.json.bak` «только если grep подтвердит, что его
никто не читает». **grep этого не подтвердил — файл живой, удаление не выполнено.**

### 5.1 `distro-lock.json.bak` — ЖИВОЙ, удалять нельзя

`lua/distro/lock.lua`:
- `:23` — `io.open(p .. ".bak", "r")`: **читается** как fallback, если основной файл
  не распарсился (возвращает `lock_err = "invalid"` → `:Distro` помечает все плагины
  `corrupted`).
- `:36` — пишется как бэкап перед каждой записью.

Вывод аудита («атомарная запись сделала `.bak` ненужным») **неверен**: атомарность
(tmp + fsync + rename) защищает от **torn**-файла, но не защищает от **битого/усечённого
вручную или диском** основного файла — fallback это единственная линия обороны.
Побайтовое сходство с основным файлом — это как раз состояние «свежий бэкап», а не
признак мусорности.

**Статус: отклонено с обоснованием. Решение за владельцем — снимать не рекомендую.**

### 5.2 `lazy-lock.json` — ЖИВОЙ, удалять нельзя

Аудит назвал файл мёртвым («grep по `lua/`, `scripts/`, `init.lua` не находит читателей»).
Grep был слишком узким. Реальные потребители:
- `flake.nix:84` — симлинкует `lazy-lock.json` в `$XDG_CONFIG_HOME/nvimdots`.
- `nixos/neovim/default.nix:152` — `bindLazyLock` (home-manager) тянет файл в машин.
- `nixos/neovim/default.nix:155` — `mergeLazyLock` + `onChange` по его хэшу.
- `.github/workflows/update_lockfile.yml:19,33,41` — CI-джоб, который **обновляет и коммитит**
  этот файл.

Файл — часть NixOS-модуля и CI. **Статус: отклонено, решение за владельцем** (как и
просил Chief of Staff — вывод записан, файл не тронут).

### 5.3 `size_kb == 0` в 24/27 записей — УДАЛЕНО

Здесь условие задания выполнено: **читателей нет**. Grep по всему `lua/` даёт только
писателей (`install.lua:429`, `tools.lua:240,273`, `treesitter.lua:214`, `ui.lua:456`) и
одну строку аннотации в `lock.lua:72`. Ни `lock.status()`, ни `lock.record()` это поле
не читают.

- `distro-lock.json`: удалены 24 ключа `"size_kb": 0` (текстово, формат и порядок ключей сохранены).
- 3 записи с реальными значениями (237 / 3312 / 4422 КБ) **оставлены** — они несут смысл.
- Проверка: 27 записей до и после, набор ключей идентичен, все `ref` сохранены,
  `lock.read()` возвращает 27 записей без ошибки. Оригинал сохранён в
  `/tmp/distro-lock.json.bak_original` (вне репозитория).

**Остаточный риск / известный побочный эффект:** поле вернётся при следующей установке —
писатели продолжают его добавлять, а `tools.lua:273` для go-бинарников пишет
захардкоженный `size_kb = 0`. То есть первопричина (захардкоженный ноль) не устранена,
а только убраны 24 мёртвых нуля из файла. Полноценное решение — либо перестать писать
поле, либо реально считать размер; это правка `install/tools`, выходящая за рамки
«чистки» и требующая решения владельца.

## 6. Что осталось риском / требует эксперимента

1. ~~**Реальная ценность пункта 1.**~~ **Снято 2026-09-25:** пункт не исполняется при

   репозитории. Нужен прогон по реальным Go-файлам: посмотреть, сколько «обычных»
   файлов теперь попадает под порог и страдает без treesitter. Рекомендую замерить
   распределение `:lua print(vim.api.nvim_buf_line_count(0))` по выборке файлов.

   удаление вендоренных файлов — это решение по упаковке, а не безопасная правка логики.

**Прочее:**
4. Основные 18 мс старта — по-прежнему тема `black-metal` (kind=`start`, eager). Не
   трогал по прямому указанию. Это остаётся крупнейшим резервом, но требует отдельного
