# Отложенная тема + откат порога large_file — 2026-09-25

Две точечные задачи. Коммита нет; чужие незакоммиченные изменения не тронуты, кроме
`init.lua` и `lua/themes/black-metal-khold.lua`, где правился **только** код отложенной
темы и гарда `termguicolors`.

---

## 1. Задача 1 — откат деградации `large_file`

**`lua/core/settings.lua:92`** — дефолт возвращён:

```lua
settings["large_file_max_lines"] = 10000   -- было 5000
```

Обоснование (та же аргументация, что у Chief of Staff, продублирована в комментарии
`settings.lua:84-91`): порог **не влияет на время старта**, только на открытие больших
файлов. Поэтому снижение 10000 → 5000 было платной деградацией без обмена — файлы
5000–9999 строк теряли treesitter и LSP.

Сохранено как было и считается верным:
- сравнение через `>=` (`lua/core/large_file.lua:26-28`);
- `0` отключает детект по строкам полностью (проверено);
- порог по размеру `large_file_max_kb` = 1024 (1 МБ) — не менялся, регрессии нет.

### Про `termguicolors` — найденный баг (важно)

Первая версия правки повесила гард на событие `ColorScheme`. **Это не работало**, и
проверка это поймала: на всех ветках `termguicolors` оставался `true`.

Причина: `termguicolors=true` ставит не `:colorscheme`, а `black-metal.load()`
(`pack/distro/start/black-metal-theme-neovim/lua/black-metal/init.lua:33`), а
`load()` вызывается **дважды** — на базовой теме и снова на кастомной
(`black-metal-khold.lua:255`), уже **после** того, как событие `ColorScheme` отыграло.
Отложенная тема вскрыла это: гард успевал отработать на старте, потом приезжала тема.

Замер по времени это показало прямо:

```
t=0    termguicolors=false colors_name=nil     <- гард отработал на старте
t=100  termguicolors=true  colors_name=khold   <- тема включила обратно, гард молчал
t=400  termguicolors=true  colors_name=khold
```

Решение: гард вынесен в `core/term_guard.lua` и вызывается **явно после каждого**
вызова темы (`black-metal-khold.lua:39` и `:255`), а не по событию. Событийная
подписка оставлена только для ручного `:colorscheme`. Идемпотентно, на обычном
терминале — no-op.

## 2.2. Гарантированный `enforce()` на всех путях отката

Ревьюер верно нашёл, что гард стоял «по успеху»: при падении
`colorscheme khold` / `black-metal.setup` / `black-metal.load` код уходил в
`habamax` и возвращался **до** `enforce()`. Это не косметика — `termguicolors=true`
ставится внутри `load()` (`black-metal/init.lua:33`), то есть **до** возможного
падения, поэтому частичный сбой оставлял 24-битный режим на dumb/screen/NO_COLOR.

Собрано так, чтобы забыть гард было **невозможно**, а не «дисциплиной»:

```lua
local function with_term_guard(fn)
	local ok, res = pcall(fn)
	pcall(function() require("core.term_guard").enforce() end)   -- всегда
	return ok, res
end
```

- `black-metal-khold.lua:30-36` — обёртка; `enforce()` стоит **после** `pcall`,
  поэтому срабатывает и при успехе, и при откате, и при неожиданном throw.
- `apply_base()` (`:45-56`) — откат в habamax **внутри** обёртки.
- `M.apply_custom` (`:293-295`) — тонкая обёртка над `apply_custom_body` (`:159`);
  оба отката в habamax внутри тела (`:257`, `:263`) теперь под гарантией.
- Прямых вызовов `require("core.term_guard").enforce()` в коде темы больше нет —
  гард существует в единственном экземпляре, добавить новый путь отката и «забыть»
  про него уже нельзя: всё применение темы ходит через `with_term_guard`.

Снято `vim.api.nvim_get_hl(0, {name=...})` для 11 групп после полного упора
(t=800 мс, то есть после базовой темы **и** кастомного прохода), флаг выключен
против включённого, реальный UI (tmux), `TERM=xterm-256color`.

## 6. Замеры (исправленная методика)

### Сначала — исправление собственной ошибки

В прошлой версии этого отчёта я назвал «шумофактором» **6.55 мс**. Это было неверно:
6.55 мс — это размах (max−min) выборки ОДНОЙ конфигурации, который смешивает
платформенный дрейф с самим эффектом. Шумофоном это быть не может. Ниже — замер
правильным методом; старую величину защищать не буду, она заменена.

Правильный шумофон = разница между двумя **байт-в-байт идентичными** конфигурациями,
прогнанными вперемежку с экспериментальной. Ниже A и B — одна и та же конфигурация
(различается только переменная окружения `TDEFER=0`), C — та же конфигурация с
`TDEFER=1`.

### Метод

- 12 пар прогонов, **свежий `--startuptime` лог на каждый запуск** (логи не
  накапливаются — это уже давало ложные числа дважды за цикл).
- **Вращающийся порядок** A/B/C в каждой итерации, чтобы дрейф машины не достался ни
  одной из групп.
- Каждый прогон — реальный UI (tmux), выход после полного упора отложенной темы.
- С флагом **выключенным** дельта нулевая по построению, время на неё не тратилось.

### Результаты (n = 12 пар)

| | A (flag off) | B (flag off, идентичная копия) | C (flag on) |
|---|---|---|---|
| best | 27.828 | 28.307 | **21.092** |
| median | 31.447 | 30.069 | **24.389** |

**Настоящий шумофон (|A−B|, идентичные копии):**

| | мс |
|---|---|
| best (мин) | **0.170** |
| median | **1.415** |
| mean | 1.908 |
| max | 5.510 |

**Эффект (A−C), парные дельты:**

`6.74, 1.80, 7.99, 5.20, 7.31, 5.47, 12.39, 6.98, 1.02, 6.66, 2.89, 9.27`

| | мс |
|---|---|
| best delta | **6.736** (27.828 − 21.092) |
| median delta | **6.697** |
| mean delta | 6.143 |
| median-to-median | 7.058 |

- **Отрицательных пар: 0 из 12** — эффект есть в каждой паре.
- **Отношение эффект/шум ≈ 5–6×** (best 6.736 / 0.170; median 6.697 / 1.415).

### Итог и оговорки

- Новая дельта: **≈6.7 мс best, ≈6.7 мс median** — это **больше** моей прошлой оценки
  4.78 мс, а не меньше. Прошлый замер был занижен: малая выборка (n=7) и неверный
  шумофон тянули оценку вниз.
- Шумофон в этом прогоне (median 1.415 мс) заметно выше ревьюерского (0.13 мс) —
  машина была шумной (каждый прогон поднимает tmux). Это делает мою оценку
  **консервативной**: эффект пережил более высокий порог шума.
- **Абсолютные числа несопоставимы с ревьюером:** у него ON≈14.9 / OFF≈20.4, у меня
  C≈24.4 / A≈31.4. Разница — в условиях прогона (у меня на каждый запуск поднимается
  tmux-сессия, что добавляет оверхед к обоим вариантам). Сравнимы **дельты**, и они
  одного порядка: его 5.53/5.83, мои 6.74/6.70.
- На SSD этот выигрыш частично съедается оверхедом GUI-прогона; на целевой HDD/VM
  ожидание выше — это **ожидание, а не замер**.

## 7. Что осталось на владельца / экспериментом

1. **Визуальная оценка вспышки — только за владельцем.** Метрика «допустима ли
   кратковременная вспышка дефолтной темы на первом кадре» не измеряется программно;
   глаз на реальном терминале. Пока флаг выключен, этого не происходит вовсе.
2. **Проверка на целевой Windows VM / HDD.** Замер сделан на macOS в tmux; реальный
   выигрыш на слабой VM и поведение первого кадра там не измерены.
3. **Стоит ли включать по умолчанию — решение владельца.** Флаг даёт ~6.7 мс ценой
   возможной вспышки; это продуктовый размен, а не чистая победа.
4. **tmux НЕ покрыт гардом termguicolors — доставшаяся по наследству дыра
   (находка ревьюера, продуктовое решение).** `term_guard.lua` матчит только
   `term:match("^screen")`, поэтому при `default-terminal=tmux-256color` гард
   молчит. Измерено при `defer_theme=true`:

   | Ветка | termguicolors |
   |---|---|
   | `TERM=screen` | `false` ✅ |
   | `TERM=screen-256color` | `false` ✅ |
   | `TERM=dumb` | `false` ✅ |
   | **`TERM=tmux-256color`** | **`true` — гард молчит** ⚠️ |

   Это **не регрессия** отложенной темы: `tmux-256color` даёт `true` и при флаге
   выключенном, то есть поведение одинаковое в обоих режимах. tmux покрывается
   только когда сам выставил `TERM=screen-*`.

   **Сознательно не расширял условие на tmux:** у пользователя с tmux, умеющим
   truecolor (настроенный `Tc` / `terminal-overrides`), принудительное выключение
   сломало бы рабочий терминал. Это продуктовый размен, а не очевидное улучшение,
   поэтому решение — за владельцем: оставить как есть (текущее состояние,
   задокументировано в `core/term_guard.lua`), либо расширить на
   `term:match("^tmux")` с пониманием, что у части пользователей 24-битный режим
   работает корректно.
5. **Порог 5000-строчных Go-файлов.** Откат дефолта убрал деградацию, но **исходная
   жалоба не решена**: 5000-строчные Go-файлы по-прежнему получают полный treesitter
   и LSP. Нужна точечная оптимизация разбора, а не порог (см.
   `docs/distro/10-largefile-analysis.md`).
6. **Неизменённое по-прежнему на владельце:** судьба фичи `sync_git_colors`,
   lock-файлы (`distro-lock.json.bak`, `lazy-lock.json`).
7. **Ветка `win32` по-прежнему не исполнялась.** `has("win32")` на macOS всегда false,
   поэтому код Windows-ветки не проверен и не выдаётся за проверенный.
