# weak-hw-2026-09-25 — переключатель gopls_* и проверка гипотезы fieldalignment

Цикл: приблизить открытие файлов и gd/gr к `nvim --clean`, приоритет — слабый ПК
(Windows VM). Основание: `docs/perf-bench-2026-09-25.md` (исследователь).

Платформа замеров: macOS 26.3 (arm64), Neovim 0.11.4, gopls v0.22.0, Go 1.26.4, тёплый
кэш. Фикстура: `gin@v1.11.0`, `/tmp/gobench/big/context.go` (1403 строки, 300 в графе),
позиция — `Context.Set` (строка 276, байт 18), **63 попадания references** во всех
вариантах. Клиент прогретый (`def_ready` = 0.2–0.3 мс — сам запрос бесплатен).

> **ГЛАВНЫЙ ВЫВОД: гипотеза исследователя ОПРОВЕРГНУТА замером.** Отключение
> `fieldalignment` (и следом codelenses и semantic tokens) **не меняет `ref_warm`**:
> 38.6 → 37.5 → 38.1 → 38.1 мс при шуме самой метрики 0.30 мс (best) / 0.55 мс
> (median). Разница в пределах шума. То есть 38 мс на `gr` — это **не фоновая работа
> gopls, с которой конкурирует запрос**, а сама стоимость references на 63-попадающем
> модуле. Переключатель сделан и полезен, но **он не лечит эту регрессию** — врать
> про обратное я не буду.

## 1. Что изменено

### 1.1 Пресет «слабое железо» (`lua/core/settings.lua:220-232`)

```lua
settings["gopls_weak_hw"] = false          -- :228
settings["gopls_weak_hw_debounce"] = 250    -- :232
```

**Отдельный флаг, а не связка с turbo** — осознанное решение. Это разные оси:
turbo про **отложивание** (поведение то же, просто позже), пресет про **содержание
работы сервера** (дешевле, но качество диагностики ниже). Один флаг на оба нельзя —
иначе нельзя получить отложивание без потери фич или наоборот.

Что покрывает: `fieldalignment` → off, все 8 codelenses → off, `semanticTokens` → off,
`completeUnimported` → off, `debounce_text_changes` → 250.

**Дефолт `false` → поведение побайтово прежнее** (проверено тестом сборки конфига,
см. §1.3). Правка обратима: удалить 2 строки настроек + условие `not weak` в 5 местах.

### 1.2 Чтение флага — ленивое, и это проверено

`lua/modules/configs/completion/servers/gopls.lua:12` — `local weak = settings.gopls_weak_hw == true`.

Модуль **не загружается на старте**: измерено, что сразу после старта (Go-файл ещё не
открывался) `package.loaded["completion.servers.gopls"] == false`. Он подтягивается
`completion/lsp.lua` при регистрации сервера, то есть **на первом Go-буфере**
(`BufReadPre`). Специально НЕ читаем флаг на этапе `core.settings` — иначе значение
запечется до того, как владелец его переключит, и `:TurboOn` / правка настроек
в середине сессии будут врать.

Честная граница: флаг читается **при первой загрузке модуля**, то есть действует на
**будущие** поднятия клиента. Уже работающий gopls не перенастраивается — это то же
поведение, что у turbo («applies to FUTURE loads»), и перезапуск сессии обязателен.

### 1.3 Ловушка codelenses закрыта

Было: `cl = settings.gopls_codelenses or {}`, затем `cl.X ~= false` для восьми ключей.
При **пустой** таблице `nil ~= false` истинно для всех восьми — то есть «ничего не
настроил» означало «включить **всё**», ровно наоборот интуиции. Владелец на это
наступает.

Стало (`gopls.lua:22-35`, функция `lens_on`):

| Что задал владелец | Результат |
|---|---|
| ключ не задан (`nil`) | всё включено (штатно) |
| пустая таблица `{}` | **все 8 выключены**, перечислять не нужно |
| `{ generate = true }` | этот включён, остальные по умолчанию включены |
| `{ generate = false }` | этот выключен, остальные по умолчанию |
| пресет `gopls_weak_hw = true` | **все 8 выключены** независимо от таблицы |

Проверено сборкой конфига во всех четырёх режимах (собственный тест, `codelenses off N/8`):
`дефолт 0/8, {} 8/8, {generate=true} 0/8, пресет 8/8`; поле `debounce_text_changes`
150 / 150 / 150 / 250. Первая версия пресета **не выключала codelenses** (0/8) — тест это
поймал, исправлено (`gopls.lua:25-27`).

## 2. Замеры: гипотеза проверена

### Метод

- **Свежий `--startuptime` лог на каждый запуск** (логи не переиспользуются).
- **A/B строго по одному изменению за прогон:** V0 (база) → V1 (+`fieldalignment=false`)
  → V2 (+`codelenses={}`) → V3 (+`semantic_tokens=false`).
- **Перемежание** с вращающимся порядком (6 позиций ротации), чтобы дрейф прогрева не
  достался ни одной группе.
- **Шумофон посчитан ОТДЕЛЬНО для каждой метрики**, на **двух байт-в-байт идентичных
  копиях конфига** (`rsync` cfgA/cfgB, `cmp -s` подтвердил идентичность), при перемежании.
  Это ровно то, чего не хватало исследователю: его «0.05–0.13 мс» для LSP-метрик **не
  подтверждается** (см. §2.2).
- n = 5 на вариант, n = 6 на каждую шумовую копию.

### 2.1 Шумофон по КАЖДОЙ метрике (A vs B, идентичные копии)

| Метрика | шум best | шум median | комментарий |
|---|---|---|---|
| `t_bufreadpost` | 0.20 | **6.45** | открытие файла шумит заметно |
| `t_lspattach` | 1.30 | **12.10** | самый шумный |
| `def_cold` | 0.10 | **7.30** | включает запуск gopls + индексацию |

| **`ref_warm`** | **0.30** | **0.55** | метрика стабильна, шум мал |

Согласуется с предупреждением исследователя: для детерминированных метрик шум мал, для
LSP-метрик — другой. `def_cold` и `t_lspattach` шумят на десятки единиц, `ref_warm` —
на доли.

### 2.3 Вердикт по гипотезе

**Опровергнута.** Ожидалось: `fieldalignment=false` срежет `ref_warm` заметно (это
гипотеза «фоновая работа gopls конкурирует с references»). Факт: −1.1 мс при шуме 0.55,
то есть **порядка шума**, а не регрессии. V2 и V3 не добавили ничего (−0.5).

Побочно: `def_cold` показал −11.7 / −8.9 / −17.3 мс, но его шум — 7.3 мс median, так что
это **не** уверенный выигрыш, а правдоподобная, но не доказанная тенденция к снижению.
Отдельно V1 −11.7 и V3 −17.3 оба крупнее шума, однако знаки скачут, поэтому честная
формулировка — «возможно небольшое ускорение холодной инициализации, требует
подтверждения на большем n».

`hits` одинаковы во всех вариантах (63 references, 1 definition) — сравнение корректно,
это не артефакт разного числа попаданий.

**Что это значит для цели владельца.** Регрессия `ref_warm` ≈ 38 мс против 0.5 мс у
голого gopls **не лечится отключением фоновых анализов**: она в самом алгоритме
references на модуле с большим графом. Переключатель остаётся полезным (он снижает
фоновую нагрузку и объём конфигурации), но **обещать по нему ускорение `gr` нельзя** —
это было бы ровно той подменой результата, ради которой цикл и затевался.

## 3. База `--clean`: проверено, утверждение исследователя верно

Исследователь отметил, что «голый gopls» — это `--clean` + явный `vim.lsp.start{gopls}`,
а не голый `--clean`, потому что в `--clean` клиент не поднимается. **Проверено
экспериментально:**

```
nvim --clean --headless -c "edit /tmp/gobench/big/context.go" … → CLIENTS=0  is_enabled=false
```

Filetype-автокоманда в `--clean` действительно **не поднимает клиента**. Значит все
цифры «против `--clean`» в отчёте исследователя — это сравнение против «голый gopls без
настроек», а база занижена относительно того, что получит пользователь на чистом
`--clean` с включённым LSP. **Вывод: цель не смещена, но формулировку «против `--clean`»
следует читать как «против минимального gopls»** — я в этом отчёте так и пишу.

Уточнение к исследователю: он указал `is_enabled=true` при `CLIENTS=0`; у меня
`is_enabled=false`. Существенная часть (клиент не поднимается) подтверждена, расхождение
в самом флаге ничего не меняет для вывода.

## 4. Что осталось недоказанным

1. **Причина регрессии `ref_warm` не установлена.** Гипотеза «фоновая работа gopls»
   опровергнута. Остаётся: сама стоимость references на 63-попадающем модуле; либо
   конфигурация, отличная от `fieldalignment`/codelenses/semtok (например
   `useany`, `nilness`, `unusedwrite`, `httpresponse`, `gofumpt` — они в пресете НЕ
   трогаются, потому что выключение `useany`/`nilness` ломает полезность диагностики).
   Следующий шаг — A/B по `analyses`, если владелец захочет копать дальше.
2. **`def_cold` −11…−17 мс не доказан** (шум 7.3 мс, n=5). Нужен больший n.
3. **Windows VM не измерялась вообще.** Все числа — macOS arm64, тёплый кэш, нижняя
   граница. На целевой VM 2–4 ядра/HDD: `def_cold` вырастет кратно (это индексация
   gopls, а не конфиг), и `ref_warm` может вырасти с 38 мс до сотен. Предупреждение
   исследователя про PATH/антивирус/Defender в силе.
4. **Визуальная оценка на слабом ПК** — только глазами владельца: что теряется при
   `gopls_weak_hw = true` (codelenses исчезают, gd не подсказывает выравнивание).
5. **win32-ветка** по-прежнему не исполнялась и за проверенную не выдаётся.
