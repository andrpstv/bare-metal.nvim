## 2. Блокеры

### B1. grepformat-фикс из 34dadee перебивается циклом ниже — :grep на Windows без rg остаётся сломанным (РЕГРЕССИЯ-НЕДОДЕЛКА)

**Файл:строка.** `lua/core/options.lua:149` ставит `"%f:%l:%m"`, а
`lua/core/options.lua:152-154` сразу после этого проходит по таблице `options`,
в которой `lua/core/options.lua:29` всё ещё лежит `grepformat = "%f:%l:%c:%m"`, и
перезаписывает значение обратно.

Порядок в функции `load_options`:
```
:140  if vim.fn.executable("rg") == 1 then
:141      set grepprg
:142      set grepformat "%f:%l:%c:%m"
:143  elseif is_win then
:149      set grepformat "%f:%l:%m"      <-- наша правка
:150  end
:152  for name, value in pairs(extend_config(options, ...)) do   <-- перезаписывает
:153      nvim_set_option_value(name, value)
```

Цикл на :152 не знает про условную логику и применяет значение из таблицы безусловно.
Ветка `elseif is_win` — мёртвый код.

**Воспроизведено** (не чтением, а исполнением; порядок строк :149 затем :152
воспроизведён дословно):
```
nvim --headless -c 'lua
  vim.api.nvim_set_option_value("grepformat","%f:%l:%m",{})
  local options = { grepformat = "%f:%l:%c:%m", fileformats="unix" }
  for name, value in pairs(options) do vim.api.nvim_set_option_value(name, value, {}) end
  print("FINAL_grepformat="..vim.o.grepformat)' -c 'qa!'
=> FINAL_grepformat=%f:%l:%c:%m
```

Значение, которое мы хотели, затёрто значением, которое хотели убрать.

**Почему это блокер, а не мелочь.** Потребитель без `rg` на Windows — это ровно тот
профиль, ради которого 34dadee и писался. У него активен `findstr`, который печатает
`file:line:text` без колонки, а `grepformat` у него `%f:%l:%c:%m`. `%c` на `text`
не резолвится — quickfix собирается с мусорной колонкой, а на файлах, где
`text` начинается с цифры, колонка может распарситься как валидная и указать
не туда. **Это в точности тот класс поломки, который 570b66c закрывал для grepprg,
но для grepformat он остался открыт.**

**Ремонт** (одна строка, не вносил — ревью только на чтение): убрать
`grepformat = "%f:%l:%c:%m"` из таблицы на `lua/core/options.lua:29` и оставить
только условные установки на :142/:149. Либо перенести цикл на :152 выше
условного блока.

**Что здесь не измерено:** правка grepformat на Windows не проверена и не может быть
проверена на этой машине (macOS, rg присутствует, `findstr` недоступен). Сам
дефект порядка строк доказан исполнением и платформа-независим — он срабатывает
на любой ОС при `is_win == true` и отсутствии rg.

### B2. `gd_to_response_ms` в `:DistroDiag` измеряет dispatch, а не ответ — ровно тот дефект, который 6fa8fde починил в трейсе

**Файл:строка.** `lua/distro/diag.lua:391-397`:
```lua
local before = vim.api.nvim_win_get_cursor(0)
local t0 = uv.hrtime()
local ok, err = pcall(pick_lsp, "definition", { jump1 = true })
local dt = (uv.hrtime() - t0) / 1e6
```
`_pick_lsp` **асинхронна** — подтверждено: `lua/keymap/pick.lua:170-215`, запрос
уходит в `vim.lsp.buf_request(...)` с колбэком и функция возвращается немедленно.
Значит `dt` — это время синхронной отправки, то есть dispatch.

Это дословно тот же дефект, который коммит `6fa8fde` описывает как
«"total" was timed right after pcall(orig) returned — but the shim dispatches
asynchronously and returns immediately» — и починил, перенеся честный TOTAL
в response-хендлер (`lua/distro/tracehooks.lua:70`). **В `diag.lua` тот же
дефект воспроизведён заново, в новом файле, после того как был назван и исправлен
в старом.**

**Проверено живьём на моей машине:**
```
gd_to_response_ms : 22.0ms
gd_jump_ms        : n/a
```
`gd_jump_ms` = `n/a`, потому что `lua/distro/diag.lua:396` сравнивает позицию
курсора сразу после возврата `pcall` — прыжок ещё не случился, он будет в
колбэке. Так что из всей «gd path» секции **ни одно число не является временем
до ответа**. Потребитель, который прочитает `gd_to_response_ms: 22.0ms` как «gd
у меня 22 мс», получит неверный вывод — ровно тот, ради устранения которого
6fa8fde и существовал.

**Ремонт:** перенести замер в колбэк, как это уже сделано в `tracehooks.lua:70` —
либо измерять через существующий `M.span`/трейс-хук, а не отдельной петлёй.
До этого `gd_to_response_ms` и `gd_jump_ms` обязаны быть помечены NOT MEASURED,
а не напечатаны числами.

### B3. Watchdog `:DistroDiag` не защищает от зависания — он сам зависает тем же способом, от которого защищает

**Файл:строка.** `lua/distro/diag.lua:626-640`:
```lua
local watchdog = uv.new_timer()
watchdog:start(120000, 0, vim.schedule_wrap(function() ... vim.cmd("qa!") end))
```
uv-таймер срабатывает только когда цикл событий Neovim крутится. Вся `run_diag`
состоит из синхронных блокирующих циклов с `vim.wait(...)`:
`lua/distro/diag.lua:341-346` (ожидание LspAttach), `:356` (settle),
`lua/distro/diag.lua:230-233` (ожидание RTT, budget 20000 мс), дважды.

`vim.wait` прокручивает цикл событий, поэтому в большинстве случаев таймер
сработает. **Но `vim.wait` не прокручивает цикл во время выполнения
blocking-вызова внутри `run_diag`, и таких вызовов два:**

1. `lua/distro/diag.lua:108` — `io.popen(gopls_path .. " version 2>&1")`.
   Это **синхронный** запуск внешнего процесса. Пока `handle:read("*a")` ждёт
   завершения `gopls version`, цикл событий не крутится и watchdog молчит.
   На HDD потребителя под Defender первый запуск gopls — это секунды, и это
   происходит **до** того, как watchdog успевает что-либо сделать.
2. `lua/distro/diag.lua:326` — `vim.cmd("edit " .. file)`. Открытие файла
   тянет ftplugins, treesitter, LSP-старт. Это синхронная работа Lua/C, и в
   худшем случае (сеть на HDD, битый кэш) она не прерывается.

**Существенно:** `io.popen` на строке 108 стоит в `header_block()`, который
вызывается на `lua/distro/diag.lua:645` — то есть **до** того, как определён
бюджет ожиданий. Это первый вызов, который делает прогон.

**Ремонт:** заменить `io.popen` на `vim.system(..., cb)` (в проекте уже есть
рабочий образец — `lua/keymap/pick.lua:111`) и ждать его через `vim.wait` с
конечным бюджетом; `vim.cmd("edit")` обернуть так, чтобы watchdog оставался
живым (например, перевести `run_diag` в `vim.schedule`-ступенях вместо одной
длинной синхронной функции).

**Главный риск из задания — «команда НЕ ДОЛЖНА зависать ни при каких условиях» —
не закрыт.** Измеренного доказательства отсутствия зависания нет: на этой машине
прогон занимает единицы секунд, а потребительский профиль (HDD, Defender, cold
gopls) в разы медленнее. Утверждение в сообщении коммита
«Watchdog on the whole run (120 s) … a partial report beats a window the user
cannot close» — это утверждение о намерении, а не о достигнутом свойстве.

### B4. `gopls_RTT2_ms` не измеряет «warm» — измеряет тот же запрос повторно

**Файл:строка.** `lua/distro/diag.lua:258-260`:
```lua
vim.api.nvim_win_set_cursor(0, { 1, 0 })
park_cursor_on_symbol()
```
Комментарий на :255 обещает «Nudge the cursor so the server is not simply
replaying a cached identical response». Но `park_cursor_on_symbol()`
(`lua/distro/diag.lua:183-192`) сканирует буфер **с первой строки** и встаёт на
первый же идентификатор — то есть **возвращает курсор в ту же позицию, что и
до первого запроса**. Nudge не происходит.

**Подтверждено измерением** (мой прогон, `stdpath("cache")/distro-diag.txt`):
```
clean project:  gopls_RTT1_ms (cold) : 12.6ms   gopls_RTT2_ms (warm) : 12.7ms
heavy import :  gopls_RTT1_ms (cold) : 12.2ms   gopls_RTT2_ms (warm) : 12.9ms
```
RTT2 не ниже RTT1, а чуть выше — в обоих случаях. Для настоящего cold/warm
различия ожидалось падение второго. Это не «шум около нуля» — обе величины
близки и обе явно помечены в отчёте как cold/warm, и потребитель прочитает
`12.6 vs 12.7` как «показатели стабильны», а не как «warm не отличается, потому
что измеряется то же самое».

**Дополнительно:** первая строка отчёта, где оба числа равны, для потребителя
неотличима от «gopls медленный и на холодную, и на тёплую». Вывод, который
напрашивается, неверный.

**Ремонт:** для warm-запроса парковать курсор на **другом** идентификаторе
(например, последнем в буфере), либо измерять на другом символе. Как есть —
строка не измеряет заявленного.

## 3. Что в f1ddefc подтверждено живьём (а не чтением кода)

Прогон выполнен на этой машине, отчёт прочитан из
`/Users/16prom1/.cache/nvim/distro-diag.txt`.

**Работает:**
- Дельты фаз считаются в порядке **фактического срабатывания автокоманд**, а не по
  таблице. Подтверждено выводом: порядок событий в отчёте —

  как список `PHASES` на `lua/distro/diag.lua:63` объявлен как

  Реальный порядок отличается от объявленного — значит используется порядок
  срабатывания, как и заявлено. Хорошо.
- Разделение `_at_ms` / `_delta_ms` работает. Пример из прогона:
  `LspAttach_at_ms : 154.2ms`, `LspAttach_delta_ms : 115.5ms`,
  предыдущее событие `BufEnter_at_ms : 38.7ms` — 154.2 − 38.7 = 115.5. Сходится.
- «Обе руки» — обе измерены, синтезированный чистый модуль работает без
  зависимости от проекта потребителя. Обе секции заполнены числами.
- `SELFCHECK: 38 measured, 0 NOT MEASURED`.
- `gd` на синтезированном буфере вернул `gd_symbol : package` — то есть
  `measure_gd_path` не сломался на отсутствии символа.
- Временные каталоги: `~/.cache/nvim/distro-diag/` после прогона **пуст**
  (`ls -laR` → только `.` и `..`). Каталоги `clean-go` и `heavy-go` удалены
  корректно. Отчёт лежит отдельно, в `distro-diag.txt`. Уборка работает.
- **Не оставляет temp за собой** — этот пункт закрыт, я проверил фактом, не кодом.
- `localappdata` на не-Windows корректно помечен `n/a (Windows-only variable)`,
  а не печатает `$HOME` под именем Windows-переменной. Правка верна.

**НЕ измерено и НЕ проверено (риск, пометить в отчёте для потребителя):**
- `%LOCALAPPDATA%` и `%TEMP%` на Windows. `lua/distro/diag.lua:88-90` читает
  `vim.env.LOCALAPPDATA`, `lua/distro/diag.lua:696` — `os.getenv("TEMP")`. На
  Windows обе переменные существуют и обе обычно заданы, так что риск низкий —
  **но это вывод по спецификации, а не наблюдение**. На этой машине ветка

  опереться, и которое этого не гарантирует.
- Тайминги на HDD/Defender. Все числа выше — с macOS SSD. Для целевого профиля
  не измерено ничего.

**`:grep` на прочих платформах** — **не сломан**.
- rg есть: `grepprg` = `rg --vimgrep`, `grepformat` = `%f:%l:%c:%m` (:141-142).
  `rg --vimgrep` даёт колонку, формат совпадает. Подтверждено косвенно:
  `nvim --headless` показывает `grepformat=%f:%l:%c:%m`, и rg присутствует.
- rg нет на *nix: `grepprg` не трогаем (платформенный дефолт — `grep -n`),
  `grepformat` остаётся `%f:%l:%c:%m` из таблицы (:29). А вот это **тоже
  неверно**: `grep -n` печатает `file:line:text` **без колонки**, а `%c`
  в формате есть. Комментарий на `lua/core/options.lua:146-148` это знает и
  говорит ровно это — «grep -n печатает file:line:text, и %c был бы лишним» —
  но код оставляет `%c`. То есть баг на *nix без rg **тот же самый**, просто
  менее заметный: `grep` есть почти везде, потребитель скорее встретит
  Windows-вариант. **B1 покрывает обе ветки** — лечится удалением строки :29.

Итог по задаче 4: `:grep` после `570b66c` + `34dadee` **не** сломан на платформах
с rg, и **сломан** на платформах без rg — то есть ровно там, куда 34dadee
направлялся.

## 5. Методическая критика — недоказанные числа в семи коммитах

Это основная ценность ревью. Ниже — конкретные места, где вывод подан как
измерение, а получен чтением кода или одиночным прогоном.

### 5.1 «gopls 9.6 %» по одному прогону — 6fa8fde

Сообщение коммита:
> «gd took 9-14 ms, of which the gopls round-trip is ~1.4 ms (9.6%) and the
> buffer-open work AFTER the response is ~12.8 ms (89%). gopls is not the
> bottleneck»

**Проблема.** 9.6 % = 1.4 / 14.5 из **одного** лога. Это n=1, без повторов,
на macOS SSD. Проценты, вычисленные от одиночного замера, наследуют всю его
ошибку и выглядят в тексте так же надёжно, как целые числа, хотя несут ровно
ту же надёжность, что и 14.5.

Особенно: `~12.8 ms (89%)` — это **остаток** `14.5 − 1.7`. Остаток в 89 % —
это утверждение «всё, что не gopls», включая всё, что вообще не измерено, а
просто не вычтено. Сумма двух процентов ровно 100 создаёт ложное впечатление
полноты картины.

**Как должно звучать:** «на одном прогоне на SSD gopls занял ~1.4 мс из ~14 мс
перехода. n=1, повторов нет, профиль — не целевой. Направление, вероятно,
верное; величина не переносится на HDD потребителя».

### 5.2 «список виновников» в том же коммите — ранжирование без разрешающей способности

Тот же коммит: «FileType, BufReadPost, LspAttach and treesitter are» — виновники.
Но сам же признаёт в пункте 1, что подстадии с `dur = nil` уезжали в низ
сортировки. То есть **до правки список виновников был получен из списка, в
котором половина элементов не сортировалась по времени вовсе**. Список
«виновников» выводился из данных, которые коммит тут же описывает как
негодные. Вывод мог быть верен по совпадению, но он не был получен из
исправленных данных — исправленные данные появились в этом же коммите, и
пересчёт по ним в сообщении не показан.

### 5.3 f1ddefc: «Verified: full headless run reports 0 NOT MEASURED» — это измерение на своей машине, подано как гарантия для потребителя

Сообщение:
> «full headless run reports 0 NOT MEASURED with both hands, gopls RTT1/RTT2,
> module counts and phase deltas»

Я подтверждаю: на **этой** машине выходит ровно `SELFCHECK: 38 measured,
0 NOT MEASURED`. Но `0 NOT MEASURED` на macOS с gopls в `$HOME/go/bin` и
модулем mongo-driver в кэше — это не то же самое, что `0 NOT MEASURED` у
потребителя. У потребителя на Windows:

- если gopls не в PATH — `lua/distro/diag.lua:98-102` даст
  `NOT MEASURED: gopls not on PATH`, и RTT не измерятся;
- если mongo-driver нет в кэше — `lua/distro/diag.lua:668` даст
  `NOT MEASURED: go.mongodb.org/mongo-driver not in module cache`, и вторая
  рука не измерится;
- если gopls не ответит за 20 с — `lua/distro/diag.lua:234-236` даст
  `NOT MEASURED ... timeout`.

То есть **самый вероятный исход у потребителя — не 0 NOT MEASURED, а
несколько**. Заявление «0 NOT MEASURED» в сообщении коммита — это измерение
своей среды, а не свойство фичи. Читатель сообщения вынесет ложное ожидание.

### 5.4 «Watchdog on the whole run (120 s)» — свойство заявлено, не обеспечено

См. **B3**. Формулировка «a partial report beats a window the user cannot
close» — это описание намерения. Доказательства, что `io.popen` на :108 и
`vim.cmd("edit")` на :326 не могут вывести watchdog из строя, нет: watchdog
зависит от кручения цикла событий, а обе эти операции его не крутят.

### 5.5 «Verified: syntax OK, config loads rc=0, smoke suite PASS» как sufficient evidence

Эта формулировка повторяется в 6fa8fde, 452c6f1, 570b66c, 864a8e8, 34dadee,
f1ddefc. `rc=0` ловит синтаксис. Smoke suite ловит наличие команд. Ни то,
ни другое не может поймать **B1** (порядок применения опций), **B2**
(асинхронная семантика), **B3** (жизнеспособность watchdog), **B4**
(идентичность двух измерений). Все четыре я нашёл чтением и прямым исполнением,
и ни один не был бы пойман заявленным «проверено». Это не ошибка автора —
это несоответствие между силой проверки и силой утверждения. 452c6f1 и 864a8e8
поступают честно и явно пишут «NOT measured end-to-end» / «подтверждены только
чтением кода» — **вот так и должно быть у всех семи**.

**Побочный факт в пользу честности части коммитов:** 452c6f1 прямо пишет
«This fix is justified by reading the call path, not by a before/after
measurement», 864a8e8 перечисляет три непроверенных пункта, 34dadee честно
описывает ложное срабатывание первой версии эвристики и то, что полноценный
рендер в headless проверить не удалось. Эта часть работы сделана хорошо —
и именно она делает расхождение в 6fa8fde и f1ddefc заметным.

## 6. Понятность отчёта для потребителя

Отчёт читает человек без нашего контекста. Оценка — **почти читаем, с тремя
оговорками**.

**Хорошо:** шапка `-- phase columns:` с расшифровкой `_at_ms` / `_delta_ms`
(`lua/distro/diag.lua:560-563`) прямо в отчёте — потребитель не обязан знать
наши соглашения. Секции `--- per-file open: <label> ---` и `--- gd path ---`
названы понятно. `SELFCHECK` даёт итог одной строкой. Формулировка
`NOT MEASURED: <причина>` самодостаточна.

**Проблема 1 — числа без единицы измерения в заголовке.** Между
`gd_to_response_ms` (B2 — это dispatch, не ответ) и реальным временем ответа
разница в разы. Потребитель не может это проверить. **Самое опасное место
отчёта.**

**Проблема 2 — `drive_kind` и `weak_hw_profile` выглядят как характеристики его
машины, но `drive_kind` использует эвристику по наличию сетевого стека**
(`lua/distro/diag.lua:150-154`), см. раздел 3. Потребитель, читающий
`drive_kind : LOCAL` на сетевом томе, получит неверный вывод о своей среде.

**Проблема 3 — сравнение двух рук не.self-explanatory.** Секции
`clean project (synthesised)` и `heavy import (go.mongodb.org/mongo-driver)`
дают числа, но в отчёте нет ни одной строки, объясняющей, **что эти две руки
значат** и что с ними делать. Потребитель видит `LspAttach_delta_ms : 115.5ms`
против `61.2ms` и не знает, это нормально, плохо или не про его случай.
Комментарий разработчика это знает (`lua/distro/diag.lua:1-40`, пункт 4:
«The project-vs-module comparison is the point of the report»), но в отчёт
это не попало. **Стоит добавить в отчёт пару строк-разъяснений.**

## 7. Вердикт по релизу

### Отдать можно сейчас

- **6fa8fde** — трейс. Дефект закрыт по существу, механизм честный, дельты и
  TOTAL считаются в правильном месте. Риск для потребителя нулевой: чисто
  наблюдательная обвязка.
- **452c6f1 + 864a8e8** — gd на внешних библиотеках. Гард на уровне модуля
  подтверждён, все ветки отказа говорят, фокус не воруется. Для потребителя это
  **чистое улучшение**: убирает блокирующий скан кэша модулей. Заявленное
  «не измерено end-to-end» в сообщениях — корректная и достаточная формулировка,
  потому что альтернатива (блокирующий скан) объективно хуже, а риск регрессии
  близок к нулю: старый путь был `vim.fn.systemlist` (блокировка), новый —
  `vim.system` с таймаутом.
- **3955abb** — заглушки dap. Списки идентичны, 15=15. Заголовочные заглушки на
  несуществующие команды убраны. Регрессии нет.
- **34dadee** — **только часть с детекцией старых логов.** Именно она работает
  и сделана аккуратно, включая честное описание ложного срабатывания первой
  версии.

### Блокирует релиз

1. **B1 — grepformat не применяется.** `lua/core/options.lua:29` перебивает
   :149. Правка 34dadec в этой части мертва, `:grep` на Windows без rg сломан —
   то есть не починен, а оставлен в том состоянии, ради которого коммит писался.
   **Блокер. Правка — одна строка.** Это единственный блокер, который
   одновременно тривиален в исправлении и критичен по охвату потребителя.
2. **B2 — `gd_to_response_ms` врёт.** `lua/distro/diag.lua:391-397`. Фича, ради
   которой потребитель будет запускать `:DistroDiag`, печатает под именем «время
   до ответа» время синхронной отправки — и печатает его уверенно, без
   NOT MEASURED. Это тот же дефект, который 6fa8fde назвал и починил в трейсе;
   здесь он воспроизведён заново.
3. **B4 — RTT2 не измеряет warm.** `lua/distro/diag.lua:258-260`. Подтверждено
   числами: 12.6/12.7 и 12.2/12.9 — warm не отличается от cold, потому что
   измеряется тот же запрос. Строка выдаёт недостоверные два числа.
4. **B3 — watchdog не гарантирует завершение.** `lua/distro/diag.lua:108`
   (`io.popen`) и `:326` (`vim.cmd("edit")`). Прямое требование задачи —
   «команда НЕ ДОЛЖНА зависать ни при каких условиях» — не выполнено и не
   обеспечено. На моей машине прогон идёт секунды; на целевом профиле (HDD,
   Defender, cold gopls) блокирующие вызовы — секунды, а watchdog в это время
   не тикает.

### Оговорка принципиальная

**Все числа в этом ревью — с macOS SSD, n=1, без повторов.** Замеры для
потребительского профиля (Windows, HDD, без turbo, без rg) **не получены**.
Следовательно:

- утверждение «gd на Windows/HDD больше не фризит» — **не измерено**;
- утверждение «:DistroDiag покажет потребителю его реальные цифры» — **не
  измерено**, а по **B2/B4** сейчас он получит как минимум две строки, которые
  означают не то, что подписаны;
- утверждение «gopls не узкое место» — **не измерено** для потребителя;
- любые проценты из раздела 5.1 — **не переносятся**.

Рекомендация: **B1 чинить немедленно** (одна строка, снимает поломку
потребителя). **B2, B3, B4 — до отправки отчёта потребителю**, иначе первый же
прогон даст ему неверные числа, и доверие к последующим замечаниям будет
потеряно. После правок — обязательный прогон `:DistroDiag` **у потребителя**,
и только его числа можно считать характеризующими его машину.

### Что проверено и не дало дефектов

- Синтаксис и загрузка конфига: `nvim --headless -c 'qa!'` — rc=0.
- Уборка временных файлов: `~/.cache/nvim/distro-diag/` после прогона пуст —
  проверено фактом, а не кодом.
- Разделение `_at_ms` / `_delta_ms` арифметически сходится (154.2 − 38.7 = 115.5).
- Порядок фаз — фактический порядок срабатывания автокоманд, не таблица.
- Обе руки измеряются; отчёт не зависит от наличия Go-проекта у потребителя.
- Правка `localappdata` корректна: вне Windows печатается `n/a`, а не `$HOME`.

### Границы ревью

Ревью только на чтение: конфиг не менялся, коммитов не делалось, кода не
писалось. Правки B1-B4 **не внесены** — только локализованы и доказаны.
Windows не проверялась (машина macOS); ветки `has("win32")` в `diag.lua` и
`is_win` в `options.lua` исполнялись только в виде статического разбора, кроме
доказанного исполнением порядка применения `grepformat` (B1), который от
платформы не зависит. Поведение `findstr` не наблюдалось. Незакоммиченные
изменения в `lua/core/settings.lua` и `lua/modules/configs/completion/lsp.lua`
в объём ревью не входили.
